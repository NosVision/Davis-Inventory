# ศูนย์บัญชาการเงินเดือน + ตารางกะรายสาขา — Design Spec

> 2026-08-28 · สถานะ: รอรีวิว
> เจ้าของโจทย์: เจ้าของระบบ (คุยผ่านแชท 2026-08-27→28) · ผู้ใช้หลัก: May (HR)

## 1. ปัญหา

HR หนึ่งคน (May) ต้องไล่ 3 หน้า — จัดตารางกะ, ตรวจเวลางาน, เงินเดือน — และแต่ละหน้ามีสวิตช์ขอบเขต
"สาขา/บริษัท" ของตัวเองที่ต้องตั้งให้ตรงกันเอง ผลที่เกิดจริง:

- ตั้งกะในโหมดบริษัทแล้วตารางสาขาว่าง → เข้าใจว่าของหาย (รายงาน 2026-08-28)
- ตั้งกะให้ทีมออฟฟิศ 10 คนที่ (ตอนนั้น) ไม่ตอกบัตร → ร่างสลิปเดือนสิงหาหักขาด 18 วัน
  ของ May เอง (−16,200 จาก gross 32,333) โดยไม่มีใครเห็นจนกว่าจะเปิดสลิป
- โมเดลในหัวของ May คือชีต Excel ต่อบริษัท: เห็นเงินเดือน+วันทำงานที่เดียว แก้ช่องแล้วสูตรวิ่ง

ข้อเท็จจริงที่หนุนการรื้อ:

| ข้อเท็จจริง | หลักฐาน (prod 2026-08-28) |
|---|---|
| เงินเดือนเป็นเรื่องระดับบริษัทล้วน | payrun ทั้ง 20 งวด (ก.พ.–ส.ค.) `store_id IS NULL` ทั้งหมด |
| ตารางกะสาขาเป็นของผู้จัดการสาขา | `hr_manager_scopes` 8 คน/5 สาขา ทุกคนถือ `can_schedule`; role staff เข้าโหมดบริษัทไม่ได้อยู่แล้ว |
| ออฟฟิศเป็นสาขาแล้ว | store "สำนักงาน (Office)" (`hr_only=true`, สมาชิก 9) — mig 00191/00192 |
| ทุก active employee มีสาขาอย่างน้อยหนึ่ง | query user_stores × hr_employees = 0 คนลอย |
| นโยบายใหม่ | **ทุกคนต้องตอกบัตร** รวมทีมออฟฟิศ (เจ้าของระบบยืนยัน 2026-08-28) |

## 2. เป้าหมาย

1. หน้าเงินเดือน = **ศูนย์บัญชาการรายบริษัท**: ทะเบียนเงินเดือน + ตาราง มา/ขาด/ลา/สาย
   ทั้งเดือนของแต่ละคน อยู่จอเดียว แก้วันได้จากตรงนั้น แล้วยอดเงินงวดร่างขยับตาม
2. หน้าจัดตารางกะ = **รายสาขาล้วน** ไม่มีปุ่มโหมดบริษัทอีก
3. ตัวเลือก **"ใช้เหมือนเดือนที่แล้ว"** สำหรับสาขาที่รูปแบบคงที่ (สำนักงานเป็นเคสหลัก)
4. ไม่มีใครต้องเข้าใจคำว่า "โหมด/ขอบเขต" อีก — ระบบรู้จากสิทธิ์ว่าใครเห็นอะไร

### Non-goals (รอบนี้ไม่ทำ)

- ไม่ยุบหน้า /hr/timesheet (คงไว้ ใช้ควบคู่ได้ ค่อยตัดสินใจภายหลัง)
- ไม่แตะสูตรเงินเดือน / กติกา OT / กติกาลา
- ไม่แตะความหมาย `user_stores` ฝั่งสต๊อก (เพิ่มสมาชิกได้ **ห้ามถอด** — ฝั่งฝากเหล้าแปลว่า "ดูแลสาขา")
- ไม่ทำ realtime — "เงินขยับตาม" = auto-recompute งวดร่างหลังบันทึก ไม่ใช่ live formula

## 3. เฟสการทำงาน

### Phase 0 — เก็บกวาดข้อมูล (migration เดียว, ไม่มีโค้ด)

1. **เพิ่ม May เข้าสาขาสำนักงาน** — `user_stores` (piyathida × Office) เธอผูก 5 สาขาแต่ไม่มี
   Office ซึ่งเป็นที่ที่เธอทำงานจริง (เพิ่มเท่านั้น ไม่ถอด 5 สาขาเดิม — ฝั่งสต๊อกต้องใช้)
2. **ย้ายกะสิงหาแบบบริษัท → แบบสาขา** — `hr_schedule` 310 แถว (`store_id IS NULL`,
   2026-08): 9 คนออฟฟิศ → store สำนักงาน; พันธุ์ธัช → store 24 BLVD
   - เงินเดือน**ไม่กระทบ**: payrun อ่านกะตาม `user_id` ไม่สนสาขา (payruns/route.ts:322)
   - unique key ของ hr_schedule ต้องตรวจว่า upsert แบบเปลี่ยน store ไม่ชนกัน (ดู §6)
3. หลังจากนี้ **ห้ามมีแถวกะแบบบริษัทเกิดใหม่** — Phase 2 ตัด UI, API ยังรับอ่านของเก่าได้

### Phase 1 — "ใช้เหมือนเดือนที่แล้ว" (คัดลอกตามรูปแบบสัปดาห์)

ปุ่มบนหน้าจัดตารางกะ (และเรียกจากศูนย์บัญชาการได้): **"คัดลอกจากเดือนก่อน"**

กติกา:
- คัดลอก **ตามวันในสัปดาห์** ไม่ใช่ตามเลขวันที่ — สำหรับแต่ละ (คน × วันจันทร์…อาทิตย์)
  เอากะ/วันหยุดที่**พบบ่อยสุด**ของวันนั้นในเดือนต้นทาง ไปเติมทุกวันเดียวกันของเดือนปลายทาง
  (เสมอกัน → เอาแบบที่เกิดหลังสุด)
- **เติมเฉพาะคนที่ยังไม่มีแถวเลย**ในเดือนปลายทาง — คนที่จัดไว้แล้วข้าม ไม่ทับ
- แถวที่สร้าง `status='draft'` ตาม convention เดิม (ต้อง publish เหมือนแก้มือ)
- ตอบกลับสรุป: เติมกี่คน กี่ช่อง ข้ามใครเพราะมีของแล้ว
- endpoint ใหม่ `POST /api/hr/schedule/copy-month` `{ store_id, from_month, to_month }`
  auth = `requireSchedulerForScope(store_id)` (ผู้จัดการสาขาใช้ได้กับสาขาตัวเอง)

### Phase 2 — หน้าจัดตารางกะเป็นรายสาขาล้วน

- ตัดปุ่มสลับ สาขา/บริษัท ออกจาก UI — เหลือดรอปดาวน์สาขาอันเดียว
  (สำนักงานอยู่ในลิสต์เหมือนสาขาทั่วไป สำหรับคนที่มีสิทธิ์)
- ผู้จัดการสาขาเห็นเฉพาะสาขาตน (พฤติกรรม `manageable-stores` เดิม) · HR เห็นทุกสาขา
- API `GET/POST/DELETE /api/hr/schedule` **ยังรับ** `company_id` ไว้อ่านประวัติเก่า
  แต่ UI ไม่ส่งอีก; แถวเก่าที่ `store_id IS NULL` ยังแสดงในศูนย์บัญชาการ (Phase 3 อ่านตามคน)
- จุดที่ต้องตาม: ลิงก์/ทางเข้าที่เคยพาไปโหมดบริษัท (HR hub, คู่มือ /guide) แก้คำอธิบาย

### Phase 3 — ศูนย์บัญชาการบนหน้าเงินเดือน (ชิ้นใหญ่)

ในทะเบียนเงินเดือนของงวด (ต่อบริษัท ที่เลือกอยู่แล้วบนหน้านั้น):

1. **กางรายคน**: แถวพนักงานกดกางได้ (มีปุ่มกางอยู่แล้วสำหรับบรรทัดสลิป) เพิ่มแท็บ/แถบ
   "เวลาทำงาน" แสดงตารางวันทั้งงวด (ภาษาภาพเดียวกับ TimesheetBlockGrid: มา/ขาด/ลา/สาย/
   OT/วันหยุด/ยังไม่ถึง) ข้อมูลจาก endpoint timesheet เดิม (คำนวณจาก punches+overrides
   เหมือน payrun เป๊ะ เพราะใช้ engine เดียวกัน)
2. **คลิกวัน → modal เดิม** (`TimesheetEditModal` ตัวเดียวกับ /hr/timesheet) — เลือก
   มา/ขาด/ลา ใส่เหตุผล มี audit ครบตามเดิม ไม่สร้าง modal ใหม่
3. **บันทึกแล้ว auto-recompute**: ถ้างวดของคนนั้นเป็น **draft** → เรียก recompute งวด
   (endpoint regenerate เดิม) แล้วรีเฟรชตัวเลขบนจอ พร้อม toast "อัปเดตยอดงวดแล้ว"
   - งวด **finalized** → แก้ไม่ได้อยู่แล้ว (period-lock ปฏิเสธที่ API; UI ปิดปุ่มพร้อมเหตุผล)
   - ยังไม่มีงวด → แก้ได้ปกติ (ไม่มีอะไรให้ recompute)
4. **คำเตือนก่อนบันทึกครั้งแรกของ session**: "การแก้นี้เขียนทับเวลาทำงานจริงของพนักงาน
   และมีผลกับแอปฝั่งพนักงานด้วย" (จำไว้ว่าเตือนแล้ว ไม่เด้งซ้ำทุกช่อง — Excel feel)
5. **กลุ่มลับ**: สืบทอดของเดิมทั้งหมด — สลิปที่ viewer ไม่มีสิทธิ์ถูกกรองที่ API อยู่แล้ว
   (`payHiddenProfileIds`), ปุ่มจัดการงวดถูกปิดด้วย `can_manage` (2026-08-27) —
   แถบเวลาทำงานของคนที่มองไม่เห็นเงินก็ไม่แสดงในทะเบียนนั้นอยู่แล้วเพราะแถวถูกกรองไป
6. **ทางลัดจัดกะ**: ลิงก์ "จัดตารางกะสาขา →" ต่อคน (ไปสาขาหลักของเขา) — ศูนย์บัญชาการ
   แก้ **วันที่ผ่านมา** (attendance/la) เป็นหลัก; การวางแผน **วันข้างหน้า** ยังทำที่หน้ากะ

### Phase 4 — กันเหตุ "ลืมตอก/ลืมตั้งกะ" ไม่ให้เงียบ (ปิดท้าย)

- การ์ดสไลซ์ในหน้าเงินเดือน เพิ่มบรรทัดเตือนจาก coverage ที่มีอยู่:
  "N คนมีวันขาด ≥ X วันในงวดนี้ — เปิดดูก่อนปิดยอด" (กันเคสสิงหาเกิดซ้ำ)
- หน้าจัดกะ: ตั้งกะให้คนที่ **ไม่เคยมี punch เลยใน 90 วัน** → แถบเหลืองบอกว่า
  "คนนี้ยังไม่เคยลงเวลา — กะที่ตั้งจะกลายเป็นขาดถ้าไม่ตอกบัตร"

## 4. สิ่งที่ต้องตัดสินใจตอนรีวิว (ยังเปิดอยู่)

- **D1**: กะสิงหาของ May เอง (21 กะ, ตอก 3 วัน) — หลัง Phase 0 ย้ายเข้าสาขาแล้ว
  ร่างงวดยังหักขาด 18 วันอยู่ดี ต้องเลือก: (ก) แก้รายวันเป็นลา/มา ตามจริง (ข) ลบกะ
  ย้อนหลังของช่วงที่ยังไม่บังคับตอก แล้วเริ่มนับจริงเดือนกันยา — **แนะนำ (ข)** สำหรับ
  ทีมออฟฟิศทั้ง 10 คน เดือนสิงหาเดือนเดียว (นโยบาย "ทุกคนต้องตอก" เริ่มนับกันยา)
- **D2**: ปุ่มคัดลอกเดือน อยู่ที่หน้ากะอย่างเดียว หรือโผล่ในศูนย์บัญชาการด้วย (แนะนำ:
  หน้ากะก่อน เฟสเดียวจบ; ศูนย์บัญชาการค่อยเพิ่มลิงก์)

## 5. สิ่งที่จงใจไม่ทำ + ความเสี่ยง

- **ไม่ realtime recompute ต่อ keystroke** — recompute ทั้งงวดใช้เวลาเป็นวินาที ยิงหลัง
  บันทึกทีละครั้งพอ (แก้ 5 ช่องติด = ยิง 5 ครั้ง ยอมรับได้; ถ้าช้าค่อย debounce)
- **ความเสี่ยงข้อมูล**: Phase 0 ย้าย 310 แถว — ทำใน migration เดียว มี rollback ง่าย
  (ย้อน store_id กลับ NULL ได้จาก audit); ตรวจ unique constraint ก่อนรัน
- **ความเสี่ยง UX**: หน้าเงินเดือนหนักขึ้น — โหลดแถบเวลาแบบ lazy ต่อคนตอนกาง ไม่โหลดรวม

## 6. เช็คก่อนลงมือ (implementation notes)

- unique index ของ `hr_schedule` = **(user_id, work_date)** ตรวจกับ prod แล้ว 2026-08-28 —
  คนหนึ่งมีแถวเดียวต่อวันไม่ว่า scope ไหน ⇒ migration Phase 0 เป็น UPDATE store_id ล้วน
  **ชนกันไม่ได้** (และยืนยันว่าความกลัว "ตั้งสองโหมดซ้อน" เกิดไม่ได้จริง — แถวหลังทับแถวแรก)
- `TimesheetEditModal` รับ context จากหน้า timesheet — ตอนฝังในหน้าเงินเดือนต้องส่ง
  leave types ของบริษัทนั้น + วันเป้าหมาย ให้ครบ (โครง props เดิมรองรับ)
- recompute งวด = `POST /api/hr/payruns` เดิม (upsert ทั้งงวด) — เช็คว่า adjustments /
  remarks / tax overrides รอด recompute (ของเดิมรอดอยู่แล้ว — ยืนยันซ้ำใน test plan)
- ทุก endpoint ที่แตะ ตรวจ `refusePayrunIfHidden` / `can_manage` ครบตามแบบ 2026-08-27

## 7. Test plan (ย่อ)

- assert: กติกาคัดลอกเดือน (weekday map, เสมอกันเอาหลังสุด, ข้ามคนมีของ, เดือน 28/31 วัน)
- assert: หลัง Phase 0 — ไม่มีแถว `store_id IS NULL` เกิน 0 ในสิงหา; payrun สิงหา recompute
  แล้วยอดเท่าเดิม byte-identical (พิสูจน์ว่าการย้ายไม่กระทบเงิน)
- E2E มือ: แก้ขาด→ลาในศูนย์บัญชาการ → ยอดหักขาดหาย, สลิปฝั่งพนักงานเปลี่ยนตาม,
  audit มีแถว, งวด finalized แก้ไม่ได้, บัญชีไร้สิทธิ์กลุ่มลับไม่เห็นแถบเวลา
